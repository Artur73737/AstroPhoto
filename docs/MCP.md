# Native MCP control

AstroPhoto 0.4.0 implements MCP in C++ inside the application executable. No Python runtime, script server, HTTP sidecar, or second camera session is involved. Both transports exist in the binary, but **only one is constructed per run**.

## Choose one transport

Close AstroPhoto, then run one of these commands from the project or distribution directory:

```powershell
./scripts/setup-mcp.ps1 -Transport http
# OR
./scripts/setup-mcp.ps1 -Transport stdio
```

Use `-Executable 'C:/path/AstroCanonController.exe'` for another installation. `-Port 47653` selects the localhost HTTP port. PowerShell 7 and the Codex CLI are required only for setup/testing; the application/MCP implementation is compiled C++.

The setup script backs up Codex's existing `config.toml`, uses the Codex CLI to replace only AstroPhoto's entry, removes obsolete `astrophoto_http`/`astrophoto_stdio` entries, and configures exactly **one** server named `astrophoto`. Other servers and preferences are preserved. Restart Codex to load the chosen connection.

### HTTP

The UI application owns `http://127.0.0.1:47653/mcp`. Setup opens it with `--mcp-http`. It must remain open for Codex to connect. A random per-user bearer token is generated by the native executable, stored under `%LOCALAPPDATA%/AstroPhoto/MCP/settings.json`, and copied into the AstroPhoto entry's `http_headers` in Codex. These files are local credentials; do not publish them.

The server binds only to loopback, verifies Host and Origin, requires the bearer token, limits request bodies, and bounds socket waits. It implements stateless Streamable HTTP with JSON responses. POST handles requests and notifications; GET returns 405 because this server does not advertise an SSE notification stream. Protocol versions 2025-11-25, 2025-06-18, 2025-03-26 and 2024-11-05 are negotiated.

### stdio

Codex launches `AstroCanonController.exe --mcp-stdio` with redirected pipes. The **same process** creates the native UI, core worker and MCP worker. No HTTP listener opens. Stdout contains only newline-delimited MCP JSON-RPC; errors go to stderr. Closing the client input ends the application through normal cleanup, including camera shutdown. Do not open another instance before Codex starts this mode.

Explicit `--mcp-http` and `--mcp-stdio` flags are mutually exclusive. Without a flag, the application reads `transport` from its per-user MCP settings. A native single-instance guard prevents simultaneously running HTTP and stdio instances. To change modes, close the current app and rerun setup; there is no live handover of a camera session.

## Thread ownership

| Application thread | Owns | Communication |
| --- | --- | --- |
| UI/main | GLFW, ImGui, OpenGL, editable UI/configuration, texture uploads and rendered screenshots | Drains a bounded `ControlQueue`; sends camera commands through `Mailbox` |
| Core | Canon SDK/session, sequence engine, stellar autofocus, measurements, captured-file decoding | Drains `Mailbox`; publishes snapshot copies, command results and decoded preview data |
| MCP | The selected HTTP **or** stdio transport, JSON-RPC parsing, schema validation, protocol replies | Submits request/reply messages to `ControlQueue`; never touches GL, ImGui or EDSDK |

The HTTP implementation uses a synchronous task queue on the MCP thread, not a thread pool. Captured-image decoding uses the existing core worker, not an extra async worker. SDK/driver/Windows threads are outside these three application-owned roles.

UI requests have bounded deadlines and capacity. Requests that expire before dispatch are never executed later. An already dispatched request can have an unknown outcome if its reply times out: inspect state before retrying a physical command. Shutdown closes the queue and wakes waiters before joining MCP. The core worker stops acquisition and disconnects on shutdown. No thread waits while holding the shared-state mutex during SDK operations, rendering or decoding.

`get_state` reports `threads.ui`, `threads.core`, `threads.mcp`, the process ID, selected transport, UI frame number and core tick counter. The counters demonstrate that rendering and core processing continue independently of MCP traffic.

## Tools

| Tools | Coverage |
| --- | --- |
| `app_status`, `app_launch`, `app_window` | Current app availability and minimize/restore/close; `app_launch` reports the already running host process |
| `get_state`, `get_settings`, `get_control_schema` | Complete camera/sequence/AF/UI state and all editable configuration schemas |
| `update_settings`, `save_settings` | Every configuration field, single-capture options, complete sequence rows, output/session/destination, labels, language/theme/scale, peaking, reticle and all stellar-AF parameters |
| `update_ui` | Live/capture selector, histogram, point-focus selection/coordinates/reset, lens step, row selection, panel visibility, collapsible sections, focus-sidebar scroll and log filters |
| `camera_connection`, `camera_properties`, `camera_set_property` | Connect/disconnect/refresh; camera-reported ISO, Av, Tv, AE, WB, Kelvin, picture style and image quality, using readable labels or actual codes |
| `live_view`, `live_zoom`, `lens_move` | Start/stop, 1x/5x/10x and one signed Canon motor step; hardware AF checks remain enforced |
| `capture_single`, `sequence_control`, `autofocus_control` | Real hardware actions through the same camera worker as the UI |
| `command_status`, `get_logs` | Queued/completed/failed acknowledgement and actual application log messages |
| `get_analysis`, `get_image` | Original RGB/Y histogram bins, point-focus metrics, raw Live View JPEG, processed preview, last captured preview, and exact rendered UI panels including overlays |
| `get_layout`, `set_layout` | Panel geometry/collapse/scroll, automatic primary-screen reset, all monitor work areas and DPI |

The schemas enumerate all settings and AF fields. `schema_version` is read-only. Native configuration validation remains the final authority, including odd AF sample counts and the mandatory **large → medium → small** drive progression. Unknown fields are rejected. Config patches merge objects; `sequence` arrays replace the whole plan. Rows contain type/count/exposure/delay/interval/Bulb/settings. An empty settings map uses the current camera values, matching the UI. Single capture uses the camera's current ISO/Av/Tv.

Configuration edits are immediately visible in the UI but are not saved until `save_settings`. Worker timing/retry/reconnection policies, custom label mappings, log capacity and initial window dimensions require saving and restarting the app. The schema response lists these fields. Configuration changes are refused while capture or autofocus is active.

Camera actions return a command ID. Poll `command_status` for **queued**, **completed** or **failed**, including the actual error. **Completed acknowledges command handling**; it does not mean a sequence or autofocus run succeeded. Inspect `get_state.state.sequence` or `get_state.state.autofocus` until the operation finishes. Result history is bounded and belongs to the current process.

`get_image(source="panel", panel="LiveView")` renders the actual native viewport to an in-memory PNG. This includes focus/sidebar graphs, peaking, histogram and reticle as currently displayed. Other panel IDs are `Toolbar`, `Connection`, `Camera`, `Sequence`, `Output`, `Log`. Sources `live`, `raw_live`, and `capture` return image data without the surrounding controls. Images are returned as MCP image content, with revision/dimension metadata. Inactive/absent previews produce an explicit error; no synthetic image is substituted. Screenshots are confined to this application's rendering, never other desktop applications.

## Validation

```powershell
ctest --test-dir out/build -C Release --output-on-failure -LE hardware
# Close AstroPhoto before the following real-process integration test:
./scripts/test-mcp.ps1
```

Unit tests cover protocol negotiation/schema completeness, invalid messages and arguments, image content, real error propagation, command acknowledgements, queue capacity, concurrent producers with isolated responses, expired-request suppression and shutdown wakeups.

The 0.4.0 Release build passed **150 CTest entries** (including the enabled real CR2 preview fixture) and **179 real-process MCP checks**. Integration PNGs and the machine-readable report are written to `out/validation/mcp/` and are not committed.

The integration script launches the real executable twice **sequentially**, once per transport. It checks distinct UI/core/MCP thread IDs inside one process, no HTTP listener in stdio mode, camera-disconnected error handling, configuration validation/rollback, UI state, native PNG screenshots, layout, HTTP authentication/Origin rejection and concurrent HTTP requests handled by the same MCP thread. It restores the in-memory settings and closes each instance cleanly; it does not connect, expose the shutter or drive a connected lens.

These tests establish control and synchronization, not optical accuracy. Stellar autofocus still needs end-to-end real-camera validation; see [hardware validation](HARDWARE_VALIDATION.md).
